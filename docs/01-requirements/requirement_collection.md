## 二、追问清单（问题 → 回答 → 结论）

### 第 1 轮：定位与边界

**Q1 目标岗位与读者** → 做 Agent + 全栈，4–5 年成熟 Java 经验，第一目标是面试官。
**结论**：首页必须在 5 秒内回答「这人是谁 + 什么技术栈 + 最拿得出手的项目」，面向技术面试官而非 HR。

**Q2 网站是主入口还是补充材料** → 只做加深印象，证明 vibe coding 能力。
**结论**：不做投递入口、不做联系表单后端；但需要 PDF 兜底能力（见 Q13 打印样式表），内容与网站同源。

**Q3 内容素材盘点** → 项目不少但偏 Java；有 1 个 RAG 项目可完整部署；后期再补 Agent demo。初期误述为「部署成本高」，经澄清为**模型 API 调用成本高**，非服务器成本。
**结论**：不做常驻在线 demo（见 Q10）。

**Q4 差异化：关掉页面后希望对方记住哪一句** → 只押一个标签。
**结论**：标签必须唯一，全站为它服务，不做「什么都会」的清单式罗列。

**Q5 范围与工期** → A（单页，1–2 天）/ B（含项目详情页，3–5 天）均可。
**结论**：最终采用 **B**（由 Q13 定死），因为标签需要靠深挖单个项目立住。

**Q6 技术栈与托管** → 倾向纯 HTML；不确定托管途径；已在 GitHub Pages 上部署过一个 blog。
**结论**：纯静态、无框架、无构建依赖为基线；托管用 GitHub Pages 起步（见 Q18）。

**Q7 公开边界** → 可以买域名；无竞业限制。
**结论**：允许公开展示项目；内部项目只写「做过什么类型的事」，不写业务数据。

### 第 2 轮：内容策略与技术方案

**Q8 标签定名（三选一）** → 选 **A**。
> **A. 「能把 Agent / RAG 从 Demo 做到能上线的工程能力」**

**结论**：放弃「vibe coding 实践者」作为标签（在部分团队是减分项），放弃「Java + Agent 复合能力」（会被追问 Agent 侧深度）。转岗最大怀疑是「只会调 API 拼 Demo」，标签 A 直接把这个怀疑变成卖点。

**Q9 「可编辑」需要哪一档**
- A：内容与页面分离（JSON/MD，改内容不碰 HTML）
- B：浏览器内编辑并保存（CMS + GitHub API）
- C：带登录的后台 + 数据库

→ 初选 **B**，后经 Q15 回退为 **A**。

**Q10 模型成本高的 demo 如何证明** → **A + C**。
- A：3 分钟演示录屏 + 架构图 + 关键代码片段
- C：一键本地复现脚本（容器编排），写明「5 分钟跑起来」
- 明确**不做** B（限流 + 密码保护的常驻 demo）

**结论**：视频负责前 10 秒的「真能跑」，脚本负责技术可信度。一个挂掉的 demo 比没有 demo 更伤。

**Q11 目标市场与站点语言** → 中文。
**结论**：单语，不做双语（双语会稀释信息密度）。

**Q12 已有 blog 的处置** → 不合并。旧 blog 很久没更新但保留；历史学习 md 本地存着，未来上传到新站。
**结论**：v1 不做文章系统，仅预留目录级扩展能力（见 Q14）。

**Q13 单页还是含详情页** → 隐含选 **B**（单页 + 项目详情页），并确认**必须加打印样式表**。
**结论**：详情页承载录屏、架构图、关键决策、量化结果。打印样式表保证面试官可一键存 PDF 转给 HR。

**Q14 现在做多深、为未来个人站留多少**
- A：单文件 index.html，未来重构
- B：目录式多页 + 内容分层（`data/profile.json`、`content/projects/*.md`）
- C：现在就搭个人站骨架（含生活/学习导航）

→ 选 **B**。C 明确否决：空壳导航会让面试官点到 404，是负分。

**Q15 浏览器内编辑怎么落地** → **放弃内置编辑器**（认为复杂度不值），改为直接在 GitHub 网页端编辑内容文件并 commit。
**结论**：GitHub 网页端即免费 CMS（有预览、有版本历史、手机可改）。页面内不硬编码任何文案，「可编辑」诉求通过内容与视图分离满足，零额外组件。

**Q16 可编辑范围** → 忽略（由 Q15 决定）。
**结论**：范围收敛为「所有展示性文案与项目内容均在内容层」，不做站内写作系统。

**Q17 RAG 项目素材盘点**

| 素材 | 现状 | 处理 |
|---|---|---|
| 演示录屏 | 未录，可录 | 待办：录 3 分钟 |
| 一键启动脚本 | 未打，可打 | 待办：docker-compose |
| 公开代码仓库 | 已有可公开代码 | 直接引用 |
| 架构图 | 未生成，可生成 | 待办：画一张 |
| 量化指标 | 仅有 RAGAS 指标 | 待办：按下方方法补齐 |

量化指标的获取方法（已给出，无需再决策）：

| 指标 | 获取方式 |
|---|---|
| 回答质量 | RAGAS：faithfulness / answer relevancy / context precision & recall，已有即可 |
| P95 延迟 | 检索前后、生成前后各打时间戳入日志，跑 50 次取分位数，**分开报检索 vs 生成** |
| Token 成本 | 模型响应 usage 字段累加 input/output tokens × 单价，得出单次问答成本 |
| 规模 | 文档数 / chunk 数 / 向量条目数 / 平均 chunk 长度，从建库脚本统计 |
| 并发能力（可选） | k6 或 locust 跑 10/20 并发，记录 QPS 与错误率 |

> 这些指标**不需要站上实时运行**，跑一次记成一张表写进详情页即可。

**Q18 域名与 URL 规划** → 域名未购买，项目刚启动。
**结论**：
- 首版直接上线 `用户名.github.io/resume_website`，域名后补（仅需加 CNAME + 改一次链接，零返工）。
- 若要一步到位：买 `.dev` 或 `.com`，**不要 `.cn`** —— `.cn` + 国内服务器必须 ICP 备案（数周流程）；`.dev`/`.com` + Cloudflare Pages / Vercel 无需备案。
- apex 域名预留给未来个人站，简历页放 `/` 或 `/resume`。

### 7.5 「问数」项目架构解读（Q24 附图）

**判定：图中链路是 workflow（固定 DAG），不是 Agent。**

链路固定为：文档/元数据召回 → 三路合并 → 过滤表与指标 → 生成 SQL → 校验 → 校正 → 执行。模型只在「生成」与「校正」两处被调用，不参与「调用谁、是否追问、何时停止」的决策。

该判定不影响项目可用性：元数据治理、混合召回、SQL 校验是真实工程底子，纯 Demo 选手没有；缺的只是模型驱动决策层，改造成本约一周，远低于另起新项目。

| # | 缺口 | 升级动作 | 面试价值 |
|---|---|---|---|
| 1 | 无歧义澄清 | 加 `ask_user` 工具，模糊表述先追问 | 体现 HITL 理解 |
| 2 | 仅一次 SQL 校正 | 改为循环：失败→读错误→重写→再校验（上限 3 轮） | 多步闭环 + 成本上限 |
| 3 | 无成本预检 | 执行前 `EXPLAIN`，拦全表扫描、强制 `LIMIT`、超时熔断 | ChatBI 最致命的坑 |
| 4 | 权限仅到表级 | 补行/列级 ACL，检索时按用户过滤 | 企业落地必答题 |
| 5 | 三路召回直接合并 | 加 rerank 或加权融合 | 与 RAG 项目方法论复用 |
| 6 | 无评测集 | 30–50 条「问题 → 期望数值」 | 标签 A 唯一的硬证据 |
| 7 | 无结果解释 | 输出「为什么是这个数」+ 图表建议 | 从能查数到能交付答案 |

**第二根柱子的形态（不新开项目，升级原项目）**：把固定流程拆成 8 个工具（search_metric / search_column / get_enum_values / get_table_schema / validate_sql / execute_sql / ask_user / explain_result），由模型自行编排，外围加路由：简单查询走原 pipeline，复杂或歧义走 Agent。

> 叙事中最值钱的一句是**路由**：「不是所有查询都该用 Agent」。能主动说明何时不该用 Agent，比会写 Agent 更能证明工程判断力。

## 八、视觉与动效需求（Q27 追加 · 待复核）

### 8.1 定位

诉求原文是「有趣、好看、动效平滑、简约」。四者中简约是可执行的约束，有趣与好看是结果，动效平滑是手段。

因此本节只做两件事：冻结**可验收的约束**与**降级规则**；把审美判断交给样张评审，不写成文字标准。

> 「好看」无法验收。硬要写进文档，只会在实现阶段变成无休止的返工。正确做法是设计阶段出 2–3 个视觉方向样张，本人选定一个后冻结该方向，之后不再临场改基调。

### 8.2 硬约束（逐条可验收）

| # | 约束 | 验收方式 |
|---|---|---|
| V1 | 色板 ≤ 3 主色 + 中性灰阶；无渐变背景、无 `box-shadow`、无玻璃拟态 | 样式表中 `linear-gradient` / `box-shadow` 出现次数为 0 |
| V2 | 字体层级 ≤ 5 级；不加载 Web Font | 无 `@font-face`、无外部字体域名 |
| V3 | 全站动效 ≤ 300ms；hover / press 120–160ms | 逐条检查 `transition` 与 `animation` 时长 |
| V4 | 只动 `opacity` / `transform` / `clip-path` / `stroke-dashoffset`；禁止动 `width`/`height`/`top`/`left` | 检查 keyframes 属性 |
| V5 | 首屏内容不得依赖动画才可见；禁用 JS 时页面完整可读 | 关闭 JS 刷新，信息零缺失 |
| V6 | 滚动揭示的元素默认可见，仅在 JS 就绪后才启用「隐藏 + 入场」 | 断网或阻断脚本，内容不消失 |
| V7 | `prefers-reduced-motion: reduce` 下全部动效关闭 | 系统开启该偏好后复查 |
| V8 | `@media print` 关闭全部动画与过渡 | `Ctrl+P` 预览 |
| V9 | 入场动效 ≤ 5 处，滚动触发 ≤ 3 处 | 计数 |
| V10 | 资源预算：CSS ≤ 12KB，JS ≤ 4KB，无第三方库 | 构建后看文件大小 |

**V5 与 V6 是本节的底线**，不是风格偏好。面试官常在手机弱网或微信内置浏览器打开，`opacity: 0` 起步等待淡入在这类环境下等于白屏，会直接摧毁「5 秒可读」这个唯一的核心目标。

### 8.3 实现方案（已定，不另行决策）

| 场景 | 实现 | 参数 |
|---|---|---|
| 首屏区块入场 | CSS `@keyframes`：`translateY(6px)` → 0 + 淡入 | 200ms，全站单一缓动曲线 |
| 滚动揭示 | 原生 `IntersectionObserver` 切换 `.in` 类，CSS transition 承接 | 250ms，位移 8px，触发阈值 15% |
| 链接 / 卡片反馈 | CSS `transition`：描边加粗、抬起 2px、下划线生长 | 140ms |
| 详情页量化表细线 | SVG `stroke-dashoffset` 描边，进入时一次 | 600ms，不循环 |
| 章节序号 01 / 02 | 纯排版，无动效 | — |

技术要点：JS 只承担两件事——打印按钮、给根元素加「就绪」类以启用滚动揭示。**JS 不参与任何内容渲染**，所以禁用 JS 时只是少了入场感，信息结构完全不变。

### 8.4 明确不做的动效

| 不做 | 理由 |
|---|---|
| 数字滚动计数 | 量化数字是可信度锚点，跳动期间读到中间值比不动更伤 |
| 视差 / 全屏转场 / 自动轮播 | 装饰性，抢注意力，与「5 秒扫读」冲突 |
| 光标跟随光斑 / 粒子背景 | 同上，且在弱设备上掉帧 |
| 打字机效果 | 推迟定位句可读时间，直接伤害首屏目标 |

### 8.5 签名元素（限 2 个，见 D15）

1. **章节序号排版**（`01 / 02`）：建立阅读节奏，零动效成本
2. **详情页量化表的描边动画**：引导视线落到最能说明问题的数字上

除这两处外，全站默认安静。

### 8.6 样张评审机制

- 设计阶段提供 2–3 个视觉方向样张，同一份内容、不同基调（如「纸面文档感」/「终端冷峻感」/「手作注记感」）
- 本人选定一个后冻结方向，后续实现不得偏离
- 样张只决定基调，不决定动效参数（动效参数已由 §8.3 锁定）
